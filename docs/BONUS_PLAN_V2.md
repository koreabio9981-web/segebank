## 2. 바이너리 매칭 실효계수 검증

**실효계수**는 같은 구매 PV가 몇 명의 상위자에게 "소실적"으로 잡혀 매칭 수당이 나가는지를 뜻합니다. 바이너리는 내 아래 모든 사람의 PV가 위로 계속 올라가며 여러 상위자에게 반복 반영되기 때문에, 조직이 깊어질수록 계수가 커집니다.

Python 시뮬레이션 결과 (활동률 60%, 이월·상한 적용 전):

| 판매원 수 | 완전 균형(최악) | 현실형(무작위 후원 + 스필오버) |
|---|---|---|
| 600명 | 2.97 | 1.81 |
| 5,000명 | 4.53 | 2.96 |
| 50,000명 | 6.20 | 3.95 |

### 2-1. 매칭률 × 실효계수 → 지급률 (삭감 전)

| 매칭률 \ 계수 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 3% | 15.3% | 17.4% | 19.5% | 21.6% | 23.7% | 25.8% |
| **5%** | 16.7% | 20.2% | 23.7% | 27.2% | **30.7%** | 34.2% |
| 7% | 18.1% | 23.0% | 27.9% | 32.8% | 37.7% | 42.6% |
| **10%** | 20.2% | 27.2% | **34.2%** | **41.2%** | 48.2% | 55.2% |

> 33% 초과 = 경보선 초과(비례 삭감), 35% 초과 = 비례 삭감이 없으면 법정 한도 초과

**읽는 법**: 회사가 커질수록 계수가 커지므로, 매칭률 10%는 **성장할수록 매달 삭감이 일상화**됩니다. 법적으로는 삭감으로 막을 수 있지만, 판매원 입장에서는 "약속한 비율보다 적게 받는" 상황이 계속됩니다. 그래서 처음부터 **5%**를 권장합니다.

## 3. 수당 규정 요약 (v0.2)

| 수당 | 계산 | 조건 | 주기 |
|---|---|---|---|
| 직추천 | 직추천 하위 구매 PV × 10% | 수당 자격 충족 | 주간 |
| 바이너리 매칭 | min(좌 실적, 우 실적) × 매칭률, **개인 월 상한 500만 원** | 수당 자격 충족 | 주간 마감 · 월 상한 |
| 롤업 | 1~N대 하위 PV × 각 1%, N = 직급별 개방 대수(3~10) | 수당 자격 충족 | 월간 |
| 직급 보너스 | 전체 PV × 3% × 내 지분 ÷ 전체 지분 | 골드 이상 | 월간 |
| 비례 삭감 | 기간 지급률 > 33%이면 모든 수당 × (33% ÷ 지급률) | 자동 | 매 정산 |

| 직급 | 누적 소실적 PV | 롤업 개방 | 지분 |
|---|---|---|---|
| 판매원 | 0 | 3대 | 0 |
| 실버 | 1,000,000 | 5대 | 0 |
| 골드 | 5,000,000 | 7대 | 1 |
| 플래티넘 | 20,000,000 | 9대 | 2 |
| 다이아몬드 | 50,000,000 | 10대 | 4 |

### 3-1. 규정서에 꼭 넣어야 할 바이너리 세부 규칙

1. **배치**: 신규 판매원을 후원인의 좌·우 어디에 둘지(추천인 지정 / 자동으로 적은 쪽 / 바깥쪽 끝)
2. **이월**: 지급 후 양쪽에서 소실적만큼 빼고, 남은 대실적은 다음 기간으로 이월
3. **플러시(소멸)**: 이월 실적의 소멸 조건. 예: [3]개월 동안 수당 자격이 없으면 소멸, 또는 이월 상한 [ ] PV
4. **개인 상한**: 월 매칭 최대 500만 원(입력 시트 C18)
5. **반품**: 반품된 PV는 좌·우 실적과 이월에서 차감하고, 이미 지급된 수당은 회수

### 3-2. 법률 확인이 필요한 조건

- **"월 본인 구매 PV 100,000 이상이어야 수당 자격"**: 매달 10만 원 이상 본인 구매를 수당 조건으로 거는 것입니다. 이것이 "자격 유지 조건의 부담"에 해당하는지, 허용 한도 안인지 **변호사 확인이 필요**합니다. 낮추거나 소비자 판매 실적도 인정하는 방법을 검토하세요.
- **비례 삭감**은 후원수당 지급기준에 명시해야 하고, 적용 결과를 판매원에게 공개해야 합니다.

## 4. 시스템 설계 추가 (바이너리)

바이너리에는 **나무가 두 개** 필요합니다. 기존 설계의 "추천 관계" 외에 "후원(배치) 관계"가 추가됩니다.

| 나무 | 쓰임 |
|---|---|
| 추천 나무(sponsor) | 직추천 수당, 롤업 |
| 배치 나무(placement, 좌·우) | 바이너리 매칭 |

```sql
ALTER TABLE members ADD COLUMN placement_parent BIGINT REFERENCES members(user_id),
                    ADD COLUMN placement_side CHAR(1) CHECK (placement_side IN ('L','R')),
                    ADD CONSTRAINT one_child_per_side UNIQUE (placement_parent, placement_side);

CREATE TABLE binary_volume (            -- 기간별 좌·우 실적과 이월
  user_id BIGINT, period DATE,
  left_new BIGINT DEFAULT 0, right_new BIGINT DEFAULT 0,
  left_carry BIGINT DEFAULT 0, right_carry BIGINT DEFAULT 0,
  matched BIGINT DEFAULT 0, paid INT DEFAULT 0, capped BOOLEAN DEFAULT false,
  PRIMARY KEY (user_id, period)
);
CREATE TABLE bonus_scaling (            -- 비례 삭감 기록
  run_id BIGINT PRIMARY KEY, ratio_before NUMERIC(6,4), scale NUMERIC(6,4), ratio_after NUMERIC(6,4)
);
```

### 4-1. 매칭 계산 (예시 코드)

```js
// 구매 확정 PV를 배치 나무 위로 올리며 좌/우 실적에 더함
function addVolume(db, buyerId, pv, period) {
  let child = buyerId, parent = db.placementParent(child);
  while (parent) {
    const side = db.placementSide(child);              // 'L' | 'R'
    db.incVolume(parent, period, side, pv);
    child = parent; parent = db.placementParent(child);
  }
}
// 마감: 소실적 × 매칭률, 개인 상한, 이월
function settleMatching(v, rule) {
  const L = v.left_new + v.left_carry, R = v.right_new + v.right_carry;
  const weak = Math.min(L, R);
  const pay = Math.min(Math.floor(weak * rule.matchRate), rule.monthlyCapRemaining);
  return { pay, left_carry: L - weak, right_carry: R - weak };  // 플러시 규칙은 별도 적용
}
// 비례 삭감: 기간 전체 수당 합계 / 순매출 > 경보선이면 모든 항목에 같은 계수
const scale = ratio > rule.alarm ? rule.alarm / ratio : 1;
```
