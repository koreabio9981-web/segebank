# 소개뱅크 개발 계획서 (설계 산출물 ⑨, v1.0)

> 설계 완료 문서를 바탕으로 **무엇을, 어떤 순서로, 얼마나 걸려** 만드는지 정합니다.
> 기간과 비용은 **추정치**입니다. 인건비·외부 요금은 계약 시점에 확인이 필요합니다.

---

> 📌 **범위 변경(2026-11-27)**: 실제 개발은 **기존 소개뱅크 프로젝트와 연동**해 진행합니다. 이 저장소는 **기본 설계와 시안**까지만 다룹니다. 아래 개발 계획과 S1 코드는 연동 시 참고용입니다.

## 1. 결론

| 항목 | 내용 |
|---|---|
| 개발 방식(추천) | **개발자 2명 + Claude Code 보조**. 기존 AWS(EC2·CodePipeline) 구조를 그대로 씀 |
| 오픈 범위(1차) | 몰 + 회원·판매원 + 판매자센터 + 수당(4종) + 오피스 + 유료회원(포인트) + 회원 개인몰(분양 A) |
| 기간 | 약 **16~18주(4개월)**. 1인이면 약 6개월 |
| 오픈 조건 | **다단계 등록증 + PG 승인 + 공제조합 연동**이 끝나야 판매원 모집·수당 기능을 켬 |
| 2차(오픈 후) | 판매자 독립몰(분양 B), 자기 도메인 연결, 솔루션 분양(C), 앱스토어 앱 |

## 2. 방식 비교

| 방식 | 기간 | 비용(추정) | 장점 | 단점 | 추천 |
|---|---|---|---|---|---|
| **2인 팀 + Claude Code** | 4개월 | 인건비 2인 × 4개월 | 빠르고, 회사에 기술이 남음 | 채용 필요 | **추천** |
| 1인 + Claude Code | 6개월 | 인건비 1인 × 6개월 | 가장 저렴 | 한 사람에게 의존, 일정 위험 | 차선 |
| 외주 개발사 | 3~5개월 | 견적(일괄) | 빨리 시작 | 수정·유지보수 비용, 수당 로직 이해 부족 위험 | 비추천 |

수당 계산은 회사의 핵심이고 규정이 바뀔 때마다 고쳐야 하므로 **내부에서 직접 관리**하는 것이 안전합니다.

## 5. 기술 구성 (확정)

| 영역 | 선택 |
|---|---|
| 화면 + API | Next.js (TypeScript) 하나의 프로젝트 |
| DB | PostgreSQL 16 (AWS RDS), 행 단위 보안(RLS)으로 사이트별 데이터 분리 |
| 작업 대기열 | pg-boss (일괄 등록, 수당 정산, 알림 발송) |
| 파일 | S3 (상품 이미지 공개 / 사업자 서류 비공개) |
| 배포 | 기존 `appspec.yml`·`buildspec.yml`·PM2 → CodePipeline |
| 테스트 | Vitest(계산 로직), Playwright(화면 흐름) |
| 수당 엔진 | 규칙 데이터(JSON, 버전 관리) + 순수 함수 계산 → 엑셀·웹 시뮬레이터와 같은 결과 검증 |

## 6. 품질 기준 (완료 정의)

1. **수당 계산**: 시뮬레이터 조직 데이터로 계산한 결과가 엑셀과 1원 단위까지 일치해야 합니다. 반품, 롤업, 소멸, 상한, 삭감 경우마다 테스트가 있어야 합니다.
2. **돈이 움직이는 모든 기능**(결제, 포인트, 수당, 출금, 정산)은 원장에 기록하고 매일 자동으로 합계를 대조합니다.
3. **권한**: 판매원·판매자·사이트 간 데이터가 섞이지 않는지 자동 테스트합니다.
4. **법정 기능 체크**: 공제번호, 35% 감시, 3개월 통지, 판매자 정보 표시, 청약철회가 모두 동작해야 합니다.
5. **모바일**: 주요 화면 Lighthouse 모바일 점수 80 이상

## 8. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| PG 다단계 업종 거절 | 결제 불가 | 2~3곳 동시 상담, 등록증 먼저 확보 |
| 공제조합 API 없음 | 공제번호 수작업 | 일괄 파일 방식 설계(예비안) |
| 수당 계산 오류 | 과다·과소 지급, 신뢰 하락 | 시뮬레이터 대조 테스트, 확정 전 관리자 검토, 이상치 경고 |
| 개발자 채용 지연 | 일정 지연 | 1인 + Claude Code로 P0~P1 먼저 시작 |
| 규정 변경 요구 | 재개발 | 수당 규칙을 데이터로 관리(코드 수정 최소화) |
