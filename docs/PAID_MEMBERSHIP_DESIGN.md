# 유료회원(포인트 충전형) 설계서 (v1.1, 설계만)

> 대표 요구사항 (2026-11):
> 1. 유료회원 금액 **150만 원**, 운영자가 수정·변경 가능
> 2. 유료회원 혜택: 판매원 자격, 수당, 직급, 할인, 상품 모두
> 3. 무료 회원 판매원 허용 여부는 **관리자가 설정**
> 4. ✅ **(v1.1 변경)** 150만 원을 내면 상품이 바로 가는 것이 아니라 **포인트가 지급되고, 그 포인트로 몰에서 판매 중인 상품을 구매**한다
>
> ⚠ 이 문서는 법률 자문이 아닙니다. "확인 필요"와 "위험 높음" 항목은 **변호사 검토 없이 확정하지 마세요.**

## 1. 결론

| 항목 | 설계 |
|---|---|
| 유료회원 흐름 | 150만 원 결제 → **쇼핑 포인트 1,500,000P 지급**(1P = 1원) → 몰에서 상품 구매 시 포인트로 결제 |
| PV·수당 발생 시점 | **포인트 충전 때가 아니라, 포인트로 상품을 사고 구매 확정될 때** |
| 포인트 종류 | **충전 포인트**(돈 내고 산 것, 환불 가능)와 **적립금**(수당·이벤트, 출금 불가)을 **완전히 분리** |
| 금액·보너스 변경 | 관리자가 변경. 수당에 영향을 주는 항목은 3개월 뒤 적용 |
| 운영 모드 | 모드 1(기본): 판매원 등록 무료, 충전은 선택 / 모드 2: 유료회원만 판매원·수당 🔒 변호사 의견서 필요 |
| 🚨 새로 생긴 법 문제 | 포인트가 **여러 판매자 상품**에 쓰이면 **선불전자지급수단 → 금융당국 등록 대상**이 될 수 있음(3장) |

### 판단 근거

1. **PV를 충전 시점에 주면 위험합니다.** 돈을 내자마자 실적과 수당이 생기면 "상품이 아니라 돈을 모아 수당을 주는 구조"(유사수신·불법 다단계)로 보일 위험이 큽니다. 실제 상품 거래가 일어날 때 PV를 주는 것이 다단계 규정(수당은 재화 판매에 연결)과도 맞습니다.
2. **35% 기준 금액**은 "판매원에게 공급한 **재화** 가격 합계"입니다. 포인트 판매는 재화 공급이 아니므로, **포인트로 상품을 산 때** 기준 금액에 들어가도록 설계합니다.
3. **충전 포인트와 수당을 섞으면 안 됩니다.** 돈 내고 산 포인트는 환불 의무가 있고, 수당은 소득이라 세금(3.3%)과 출금 규칙이 다릅니다.

## 2. 전체 흐름

```text
① 유료회원 가입(150만 원 결제, PG)
     → 충전 포인트 1,500,000P 지급 (+ 보너스 포인트: 관리자 설정, 기본 0%)
     → 회계: 선수금(부채). 아직 매출 아님. PV 없음
② 몰에서 상품 선택 → 결제 수단: [포인트] [포인트 + 카드]
     → 포인트 차감(유효기간 임박분부터)
③ 배송 → 구매 확정
     → 이때 매출 인식 + PV 적립 + 수당 계산 대상 + 35% 기준 금액에 포함
     → 공제번호: 상품 거래 시 발급(포인트 판매 시점에도 필요한지 확인 필요)
④ 반품 → 사용한 포인트 복원(유효기간 그대로) + PV·수당 회수
⑤ 남은 포인트 환불 신청 → 약관 기준으로 잔액 환불(4-3)
```

## 3. 🚨 선불전자지급수단 규제 (반드시 검토)

### 3-1. 확인된 내용 (금융위원회·금융감독원 자료, 2024-09-15 시행 개정법 기준)

| 항목 | 내용 |
|---|---|
| 등록 면제 조건 | 분기말 발행잔액 **30억 원 미만** + 연간 총발행액 **500억 원 미만** + **가맹점이 1개**인 경우 |
| 가맹점 기준 | 예전에는 가맹점 10개 이하면 면제였지만, **지금은 1개일 때만** 면제 |
| 미등록 발행 | 3년 이하 징역 또는 2천만 원 이하 벌금 |

### 3-2. 소개뱅크에 미치는 영향

| 구조 | 포인트 사용처 | 판단(확인 필요) |
|---|---|---|
| **소개뱅크가 직접 판매자**(입점 판매자 상품도 소개뱅크가 매입·위탁받아 소개뱅크 이름으로 판매) | 가맹점 1개(소개뱅크) | 면제 가능성 있음(금액 기준 충족 시) |
| **오픈마켓**(입점 판매자가 각자 판매 주체, 소개뱅크는 중개) | 가맹점 여러 개 | **선불업 등록 대상 가능성 높음** |
| 분양 C 업체에서도 사용 | 다른 회사 | **등록 대상**. → 포인트는 **사이트(tenant)별로 분리**, 서로 사용 불가 |

### 3-3. 설계 대응

1. **포인트 사용 가능 상품 설정**: 상품마다 "포인트 결제 가능" 표시. 기본은 **소개뱅크가 판매 주체인 상품만** 사용 가능.
2. **판매 주체 구조 결정이 먼저**입니다. 판매자센터·정산 설계(위탁 판매인지 중개인지)가 여기에 맞춰 바뀝니다. **변호사·세무사 확인이 필요합니다.**
3. **발행잔액 모니터링**: 관리자 대시보드에 분기말 발행잔액과 연간 총발행액을 표시하고, 면제 기준의 80%에 도달하면 경고합니다.
4. 등록이 필요해지면 이용자 충전금 보호 의무(별도 관리 등)가 생깁니다. 세부 의무는 확인이 필요합니다.

## 4. 포인트 설계

### 4-1. 포인트 종류

| 구분 | 충전 포인트 | 적립금 | 수당(참고) |
|---|---|---|---|
| 얻는 방법 | 유료회원 결제, 추가 충전 | 이벤트, 구매 적립 | 수당 규정에 따라 |
| 사용처 | 포인트 결제 가능 상품 | 상품 구매 | **원화 출금** |
| 환불 | **가능**(4-3) | 불가 | 해당 없음 |
| 유효기간 | 5년(확인 필요) | 관리자 설정(예: 1년) | 해당 없음 |
| 다른 회원에게 보내기 | **불가**(기본) | 불가 | 불가 |
| 현금화 | 환불 외 불가 | 불가 | 출금 |

> 참고 사이트에 있던 **"포인트 전송하기"는 넣지 않습니다.** 회원끼리 돈처럼 주고받는 수단이 되면 선불업·유사수신·자금세탁 위험이 커집니다. 꼭 필요하면 변호사 검토 후 관리자 설정으로만 켭니다.

### 4-2. 보너스 포인트 (관리자 설정)

- 예: 150만 원 충전 시 **+5% = 75,000P** 추가.
- **상한 10%**를 설정값으로 둡니다. 그 이상이면 저장할 때 경고합니다. 큰 보너스는 "원금보다 많이 돌려준다"는 투자처럼 보일 수 있기 때문입니다.
- 보너스 포인트는 **환불하지 않고**, 먼저 사용되며, 유효기간이 짧습니다(설정).
- 보너스 비율 변경은 수당과 무관하면 즉시 적용, 새 충전부터 적용합니다.

### 4-3. 환불 규칙 (약관 초안, 확인 필요)

| 경우 | 처리 |
|---|---|
| 충전 후 7일 이내, 전혀 사용 안 함 | **전액 환불**(청약철회) |
| 일부 사용 후 환불 요청 | 남은 충전 포인트를 원화로 환불(보너스 포인트 제외). 소액 수수료 여부는 약관·법 확인 필요 |
| 유효기간 지남 | 소멸 전 30일·7일에 알림 |
| 탈퇴 | 남은 충전 포인트 환불 후 탈퇴 |
| 모드 2에서 환불 | 판매원 자격·직급 회수(규정서에 명시) |

## 5. 운영 모드 (관리자 설정)

| 동작 | 모드 1 (기본, 권장) | 모드 2 🔒 |
|---|---|---|
| 판매원 등록 | 누구나 무료 | 150만 원 충전한 회원만 |
| 수당 | 판매원 전체(구매 확정 매출 기준) | 유료회원만 |
| 개인몰(분양 A) | 판매원 누구나 | 유료회원만 |
| 충전 | 선택(혜택: 보너스·할인) | 판매원 조건 |
| 잠금 해제 | — | 변호사 의견서 업로드 + 대표 2단계 인증 + 적용일 3개월 후 + 전체 통지 |

모드 2가 위험한 이유: 판매원 **등록·자격 조건으로 일정 수준을 넘는 비용을 부담시키는 것**은 방문판매법 금지 행위입니다. 허용 한도는 확인이 필요합니다. 포인트로 돌려받는 구조여도 "등록하려면 150만 원을 먼저 내야 한다"는 점은 같습니다.

## 7. 데이터 구조

```sql
-- 유료회원 상품 (버전 관리)
CREATE TABLE membership_plans (
  id BIGSERIAL PRIMARY KEY, tenant_id BIGINT NOT NULL DEFAULT 1,
  code VARCHAR(20) NOT NULL, version INT NOT NULL,
  name VARCHAR(60) NOT NULL,
  price INT NOT NULL,                 -- 1500000
  points INT NOT NULL,                -- 1500000
  bonus_rate NUMERIC(5,2) DEFAULT 0,  -- 최대 10 권장
  member_discount NUMERIC(5,2),
  charge_valid_months INT DEFAULT 60, bonus_valid_months INT DEFAULT 12,
  grant_grade VARCHAR(20),            -- 모드 2에서만
  effective_from TIMESTAMPTZ NOT NULL, status VARCHAR(10) DEFAULT 'SCHEDULED',
  UNIQUE (tenant_id, code, version)
);

-- 포인트 묶음: 충전할 때마다 1줄 (유효기간·환불 가능 여부를 묶음 단위로 관리)
CREATE TABLE point_lots (
  id BIGSERIAL PRIMARY KEY, tenant_id BIGINT NOT NULL DEFAULT 1,
  user_id BIGINT NOT NULL REFERENCES users(id),
  kind VARCHAR(10) NOT NULL,          -- CHARGE(충전) / BONUS(보너스) / REWARD(적립금)
  amount INT NOT NULL, remaining INT NOT NULL CHECK (remaining >= 0),
  refundable BOOLEAN NOT NULL,        -- CHARGE만 true
  source_order_id BIGINT,             -- 충전 결제 주문
  expires_at TIMESTAMPTZ NOT NULL, created_at TIMESTAMPTZ DEFAULT now()
);

-- 포인트 사용·복원·환불·소멸 기록 (모든 변화는 여기에 1줄)
CREATE TABLE point_tx (
  id BIGSERIAL PRIMARY KEY, lot_id BIGINT REFERENCES point_lots(id),
  user_id BIGINT NOT NULL, kind VARCHAR(10) NOT NULL,   -- ISSUE/USE/RESTORE/REFUND/EXPIRE/ADJUST
  amount INT NOT NULL,                                  -- +늘어남 / -줄어듦
  order_id BIGINT, memo TEXT, created_by BIGINT, created_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE memberships (
  id BIGSERIAL PRIMARY KEY, user_id BIGINT REFERENCES users(id),
  plan_id BIGINT REFERENCES membership_plans(id), charge_order_id BIGINT,
  status VARCHAR(10) NOT NULL,        -- ACTIVE / REFUNDED
  started_at TIMESTAMPTZ, ended_at TIMESTAMPTZ
);

-- 상품: 포인트 결제 가능 여부
ALTER TABLE products ADD COLUMN point_payable BOOLEAN NOT NULL DEFAULT false;
-- 주문: 결제 수단별 금액
ALTER TABLE orders ADD COLUMN paid_points INT NOT NULL DEFAULT 0, ADD COLUMN paid_cash INT NOT NULL DEFAULT 0;
```

### 7-1. 포인트 사용 순서 (예시 코드)

```js
// 주문 결제: 보너스 → 적립금 → 충전 포인트 순, 같은 종류는 유효기간 임박분부터
async function usePoints(t, userId, orderId, need) {
  const lots = await t.any(`SELECT * FROM point_lots WHERE user_id=$1 AND remaining>0 AND expires_at>now()
    ORDER BY CASE kind WHEN 'BONUS' THEN 1 WHEN 'REWARD' THEN 2 ELSE 3 END, expires_at FOR UPDATE`, [userId]);
  for (const lot of lots) {
    if (need === 0) break;
    const use = Math.min(lot.remaining, need);
    await t.none('UPDATE point_lots SET remaining=remaining-$2 WHERE id=$1', [lot.id, use]);
    await t.none(`INSERT INTO point_tx(lot_id,user_id,kind,amount,order_id) VALUES($1,$2,'USE',$3,$4)`, [lot.id, userId, -use, orderId]);
    need -= use;
  }
  if (need > 0) throw new HttpError(400, '포인트가 부족합니다');
}
```

보너스를 먼저 쓰게 하는 이유는 환불 대상(충전 포인트)을 최대한 남겨 소비자에게 유리하게 하기 위해서입니다.

```text
│ 사용 내역                  │
│ 11-26 충전  +1,500,000     │
│ 11-26 보너스   +75,000     │
│ 11-27 김치 5kg  -58,900    │
├──────────────────────────┤
│ [남은 포인트 환불 신청]       │
└──────────────────────────┘
```

## 9. 수당·35% 한도와의 관계

1. **PV는 포인트로 산 상품이 구매 확정될 때** 생깁니다. 충전 시점에는 생기지 않습니다.
2. 35% 기준 금액에는 **포인트로 구매한 상품 가격**이 들어갑니다. 충전 금액은 들어가지 않습니다.
3. 관리자 설정 중 "충전 시 PV 지급"은 **만들지 않습니다.** 꼭 필요하면 변호사 의견서가 있을 때만 켜는 모드 2 계열 잠금 기능으로 따로 검토합니다.
4. 대시보드에 **"충전 대비 실제 상품 구매율"**을 표시합니다. 충전만 많고 구매가 적으면 상품이 아닌 돈 모집으로 보일 위험이 있습니다.

## 10. 발생할 수 있는 문제와 해결

| 문제 | 해결 |
|---|---|
| 선불업 미등록 발행 | 포인트 사용처를 소개뱅크 판매 상품으로 제한, 발행 규모 모니터링, 기준 근접 시 등록 준비 |
| 충전만 하고 상품 구매가 적음 | 구매율 대시보드, 유효기간 알림, 환불 안내 |
| 회원끼리 포인트를 돈처럼 거래 | 전송 기능 없음, 계정 양도 금지 약관 |
| 포인트 잔액 계산 오류 | 묶음(lot)과 기록(tx) 이중 관리, 매일 합계 대조 |
| 환불 분쟁 | 결제 화면에 환불 규칙 명시, 7일 청약철회, 잔액 환불 |
| 반품 시 포인트 처리 | 사용했던 묶음에 그대로 복원(유효기간 유지) + PV·수당 회수 |

## 11. 변호사·세무사에게 꼭 물어볼 것

1. 150만 원 충전 포인트가 **선불전자지급수단**에 해당하는지, 판매 구조(직접 판매 / 중개)에 따라 달라지는지
2. **판매원 등록·자격 조건으로 받을 수 있는 비용의 허용 한도**, 충전 방식도 여기에 해당하는지(모드 2 가능 여부)
3. 충전 포인트 **환불 규칙과 유효기간**(5년 적정 여부), 보너스 포인트 처리
4. **공제번호 발급 시점**: 포인트 판매 때인지, 상품 구매 때인지
5. 35% 기준 금액 산정: 포인트 결제 상품, 비회원 소비자 매출 포함 여부
6. **회계·세금**: 충전 금액 선수금 처리, 부가세 과세 시점(포인트 판매 vs 상품 구매)
