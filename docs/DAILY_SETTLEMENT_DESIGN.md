# 일간 정산 · 실시간 수당 포인트 설계 (v1.0)

> 규칙: [기준서 v0.4 변경안](BONUS_RULES_V0.4.md) · 데이터: [schema.sql](dev/schema.sql) · 개발: [개발 설계서](dev/TECH_SPEC.md)

---

## 1. 결론

| 항목 | 설계 |
|---|---|
| 회원 화면 | **내 포인트 지갑** 하나에 모두 표시: **출금 가능** · **출금 불가(정산 대기 / 쇼핑 전용)** · 예상 수당 |
| 실시간 | 결제 즉시 "예상 수당"이 보이고, 구매 확정 다음 날 새벽 정산으로 **수당 포인트에 적립** |
| 정산 | 매일 00:30에 전날 구매 확정분을 정산. **90% 출금 가능 + 10% 정산 대기** |
| 월말 확정 | 그달 지급률 ≤ 33%면 다음 달 3일에 정산 대기분을 출금 가능으로 옮김. 넘으면 정산 대기분에서 조정 |
| 출금 | 회원이 신청(1만 원 이상, 1천 원 단위) → 원천징수 3.3% → 다음 영업일 이체 |

## 2. 돈의 흐름 (타임라인 예시)

```text
11/03 10:00  하위 판매원 결제 (PV 70,000)
             → 내 화면: "예상 수당 +7,000P (구매 확정 후 정산)"           ← 실시간, 잔액 아님
11/06 18:00  배송 완료
11/13 04:00  자동 구매 확정 (7일 경과)
11/14 00:30  일간 정산 (11/13 확정분)
             → 수당 7,000P 확정: 출금 가능 +6,300P / 정산 대기 +700P     ← 알림 발송
11/14 09:00  출금 신청 50,000원 → 원천징수 1,650원 → 11/15 48,350원 입금
12/01        11월 지급률 계산: 23.7% (≤ 33%)
12/03        11월 정산 대기 → 출금 가능으로 이동 (+700P)
```

지급률이 넘는 경우(예: 11월 36%):
- 조정 계수 = 33 ÷ 36 = 0.9167입니다.
- 11월 수당 총액의 8.33%만큼 정산 대기분에서 뺍니다(정산 대기 10% 중 8.33%).
- 남은 1.67%는 출금 가능으로 옮깁니다.
- 지급률이 36.7%를 넘으면 정산 대기분으로 부족합니다. 이때는 다음 달 수당에서 뺍니다.

## 3. 포인트 지갑 잔액 구조

| 구분 | 내용 | 출처 | 출금 | 쇼핑 결제 |
|---|---|---|---|---|
| **출금 가능** | 확정 수당의 90% + 월말 해제분 − 출금·회수 | 수당 원장(AVAILABLE) | ✅ | 별도 결정 `[법률 확인]` |
| 출금 불가 · **정산 대기** | 확정 수당의 10% (월말 확정 전) | 수당 원장(RESERVED) | ❌ (월말 후 이동) | ❌ |
| 출금 불가 · **쇼핑 전용** | 충전 포인트, 보너스 포인트, 적립금 | 포인트 묶음(point_lots) | ❌ (충전분만 환불 규정) | ✅ |
| (참고) **예상 수당** | 결제됐지만 구매 확정 전 | 계산값(bonus_estimates) | 잔액 아님 | ❌ |

**원칙**
- **수당 포인트**와 **쇼핑 포인트**는 다른 원장입니다. 서로 바꿀 수 없습니다.
- 화면에서는 한 지갑에 모아 보여 주되, 구분을 분명히 표시합니다.

## 4. 처리 순서

### 4-1. 실시간 (결제·확정·반품 시)

1. 결제 완료: `bonus_estimates`를 생성합니다.
   - 구매자 위 추천 라인(직추천, 롤업)과 후원 라인(매칭 예상)을 계산합니다.
   - 매칭은 "예상 최대" 값으로 표시합니다(소실적은 정산 때 결정).
2. 취소·반품: 해당 예상을 VOID 처리합니다.
3. 구매 확정: 예상을 CONFIRMED_PENDING으로 바꿉니다(다음 정산 대상).
4. 화면 반영: 회원 화면은 화면 갱신이나 짧은 주기(30초)로 새 값을 가져옵니다.

### 4-2. 일간 정산 (매일 00:30, 작업 `bonus.daily`)

```text
1. 대상: 전날 구매 확정된 order_items (pv_eligible) + 전날 반품분(회수)
2. 자격: 각 판매원의 직전 30일 PV(본인 + 개인몰 소비자) ≥ 100,000
3. 수당 엔진(순수 함수) 실행 → bonus_items (직추천·매칭·롤업·직급 보너스)
   - 매칭 월 상한: 그달 누적 지급액 확인
4. 원장 기록 (한 트랜잭션):
   earnings_ledger  +90% AVAILABLE  (DAILY_ACCRUAL)
                    +10% RESERVED   (DAILY_ACCRUAL)
                    −회수액 AVAILABLE (CLAWBACK, 월말 전이면 RESERVED에서 먼저)
5. bonus_estimates → SETTLED, 알림("어제 수당 12,300P 적립")
6. 이상치 검사: 하루 지급률이 평소의 2배 이상이거나 1인 급증 → 관리자 알림
   (자동 정산은 진행하고, 출금만 잠시 보류 가능)
```

### 4-3. 월말 확정 (매월 1일 03:00 계산 → 3일 반영, 작업 `bonus.monthlyTrueup`)

```text
ratio = 그달 bonus_items 합계 / 그달 순매출(PV 대상 공급가, 반품 차감)
if ratio <= 0.33: RESERVED 전액 → AVAILABLE (RESERVE_RELEASE)
else:
  scale = 0.33 / ratio
  각 판매원 조정액 = 그달 수당 × (1 − scale)
  RESERVED에서 조정액 차감(SCALING_ADJ), 남은 RESERVED → AVAILABLE
  RESERVED로 부족하면 부족분을 다음 달 첫 정산에서 차감(CARRY_ADJ)
관리자 검토 → 확정(3일 00:00 반영) · 결과를 판매원 화면에 표시
```

### 4-4. 출금

```text
회원 신청(재인증: 비밀번호 또는 지문) → 검사
  - 출금 가능 잔액 ≥ 신청액, 1만 원 이상·1천 원 단위
  - 주민번호·계좌 등록 확인 → 미등록이면 등록 화면으로 안내
→ 원장: AVAILABLE −신청액 (WITHDRAW_HOLD)
→ 매 영업일 16:00 마감: 그날 신청 건을 이체 배치로 묶음(관리자 2인 승인 또는 자동 승인 규칙)
→ 이체 성공: WITHDRAW_PAID + WITHHOLDING 기록 / 실패: WITHDRAW_FAIL로 잔액 복원·알림
```

자동 승인 규칙(관리자 설정 예):
- 1건 100만 원 이하이고 최근 30일 이상치 경고가 없으면 자동으로 배치에 넣습니다.
- 그 밖에는 관리자가 확인합니다.

## 5. 데이터 구조 변경 ([schema.sql](dev/schema.sql) 반영)

| 표 | 변경 |
|---|---|
| `earnings_ledger` | `bucket`(AVAILABLE / RESERVED) 추가. 종류를 DAILY_ACCRUAL · RESERVE_RELEASE · SCALING_ADJ · CARRY_ADJ · CLAWBACK · WITHDRAW_HOLD · WITHDRAW_PAID · WITHDRAW_FAIL · WITHHOLDING · ADJUST로 변경 |
| `bonus_runs` | 종류에 DAILY · MONTHLY_TRUEUP 추가. `reserve_rate` 추가 |
| `bonus_estimates` (신규) | 실시간 예상 수당 (주문상품, 받을 판매원, 종류, 예상액, 상태) |
| `withdrawals` (부활) | 회원 출금 신청 (신청액, 원천징수, 실지급, 상태, 배치) |
| `payout_items` | 출금 신청 1건 = 1항목 (배치 이체용) |
| `qualification_daily` (신규) | 판매원별 날짜별 직전 30일 PV와 자격 여부 |

잔액은 원장 합계로 계산합니다. 화면 속도를 위해 `earnings_balances` 뷰(또는 매일 갱신하는 요약표)를 둡니다.

## 6. 화면

| 영역 | 화면 | 내용 |
|---|---|---|
| 오피스·몰 | **내 포인트 지갑** | 출금 가능 / 출금 불가(정산 대기, 쇼핑 전용) / 예상 수당, [출금 신청] [쇼핑하기] |
| 오피스 | 수당 내역 | 날짜별 수당(종류별), 월말 확정 결과(지급률, 조정 계수), 예상 → 확정 상태 |
| 오피스 | 출금 신청·내역 | 금액, 원천징수 3.3%, 실지급, 계좌, 상태 |
| 관리자 | 일간 정산 | 오늘 정산 결과, 지급률, 이상치 |
| 관리자 | 월말 확정 | 그달 지급률, 조정 계수, 정산 대기 해제·조정 실행 |
| 관리자 | 출금 승인·배치 | 오늘 신청, 자동 승인 대상, 2인 승인, 이체 결과 |

## 7. 발생할 수 있는 문제와 해결

| 문제 | 해결 |
|---|---|
| 하루 단위 지급률 출렁임 | 일간은 유보 10%로 완충, 법정 판단은 월말·연간 |
| 월말 지급률이 36.7%를 넘어 유보분이 부족 | 다음 달 차감(CARRY_ADJ) + 관리자 경고, 수당 구조 재검토 신호 |
| 출금 후 반품으로 잔액 마이너스 | 이후 수당에서 차감, 마이너스 동안 출금 불가 |
| 예상 수당과 확정 수당 차이 | 화면에 "예상(변동 가능)" 명시, 매칭은 소실적으로 확정됨을 안내 |
| 매일 이체 업무 부담 | 자동 승인 규칙 + 영업일 1회 배치 |
| 수입 시기·원천징수 시점 | 정산 시점 vs 출금 시점 `[세무 확인]`. 시스템은 둘 다 기록 |

## 8. 테스트 기준

1. 같은 한 달 데이터로 계산한 **일간 정산 합계**가 같은 기간을 **한 번에 계산한 결과와 1원 단위로 같아야** 합니다. 매칭 이월·상한이 일 단위로 바뀌는 차이는 기준서에 맞춰 검증합니다.
2. 월말 지급률 23.7%(해제), 34%(일부 조정), 40%(다음 달 차감) 세 경우를 시험합니다.
3. 출금 → 반품 회수 → 잔액 마이너스 → 다음 수당 차감 흐름을 시험합니다.
4. 원장 합계 = 지갑 화면 잔액(매일 대조 작업)을 확인합니다.
